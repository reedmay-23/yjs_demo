# 文档访问权限与共享设计

## 1. 当前状态

当前项目已经有文档创建、文档列表、删除文档、协同连接和在线会话记录能力，但还没有真正的“共享文档/添加协作者”功能。

现有权限规则：

- 文档创建者可以访问文档。
- 非创建者不能访问文档。
- `/collab1` 和 `/collab2` 在建立 WebSocket 房间前都会校验文档权限。
- `/document/getList` 只返回当前用户创建的文档。
- `collaboration_sessions` 只记录协同在线会话，不是授权表。

当前核心判断在 `YjsStorageService.validateDocumentAccess`：

```ts
document.createdBy === userId
```

这意味着即使用户拿到 `docId`，只要不是创建者，也不能进入协同房间。

## 2. 设计目标

新增文档共享权限体系，支持：

- 文档创建者可以把文档分享给其他用户。
- 被分享用户可以在自己的文档列表里看到该文档。
- 被分享用户可以进入协同编辑房间。
- 创建者可以移除协作者。
- 后续可以扩展只读、编辑、管理等角色。

设计原则：

- 授权数据和在线会话数据分离。
- 协同服务只依赖统一的权限校验方法。
- HTTP 接口和 WebSocket 使用同一套权限规则。
- 默认不改变现有创建者权限。

## 3. 数据模型设计

新增一张文档协作者表，建议命名为 `document_collaborators`。

Prisma 设计示例：

```prisma
model DocumentCollaborator {
  id         Int      @id @default(autoincrement())
  documentId Int      @map("document_id")
  userId     Int      @map("user_id")
  role       String   @default("editor") @db.VarChar(32)
  createdBy  Int      @map("created_by")
  createdAt  DateTime @default(now()) @map("created_at")
  updatedAt  DateTime @updatedAt @map("updated_at")

  document Document @relation(fields: [documentId], references: [id], onDelete: Cascade)
  user     User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  inviter  User     @relation("DocumentCollaboratorInviter", fields: [createdBy], references: [id])

  @@unique([documentId, userId])
  @@index([documentId])
  @@index([userId])
  @@map("document_collaborators")
}
```

建议角色：

| role | 含义 |
| --- | --- |
| `owner` | 文档创建者，不需要写入协作者表，直接由 `documents.createdBy` 表示 |
| `editor` | 可查看、可编辑、可进入协同 |
| `viewer` | 可查看，只读协同，后续需要配合前端和 WebSocket 写权限控制 |

第一阶段可以只实现 `editor`，先把共享协同跑通。

## 4. 权限判断规则

统一封装一个文档权限判断方法，例如：

```ts
validateDocumentAccess(docId, userId, requiredRole?)
```

判断顺序：

1. 查询文档是否存在。
2. 如果 `document.createdBy === userId`，直接允许，身份为 `owner`。
3. 查询 `document_collaborators` 是否存在 `documentId + userId` 记录。
4. 如果存在并满足角色要求，允许。
5. 否则拒绝访问。

第一阶段规则：

```text
owner: 全部权限
editor: 可查看、可编辑、可协同
viewer: 暂不实现，或仅作为预留
```

权限方法不要散落在 controller 或 gateway 里，应该集中在 service 里。这样 `/document`、`/yjs-storage`、`/collab1`、`/collab2` 都能复用。

## 5. 接口设计

### 5.1 添加协作者

```http
POST /document/:docId/collaborators
Authorization: Bearer <accessToken>
Content-Type: application/json

{
  "userId": 2,
  "role": "editor"
}
```

权限要求：

- 只有文档创建者可以添加协作者。
- 不能添加不存在的用户。
- 不能重复添加同一个用户。
- 不建议把创建者自己添加为协作者。

成功响应：

```ts
{
  data: {
    id: number;
    documentId: number;
    userId: number;
    role: "editor";
    createdBy: number;
    createdAt: string;
  },
  message: "添加协作者成功",
  code: 0
}
```

### 5.2 获取协作者列表

```http
GET /document/:docId/collaborators
Authorization: Bearer <accessToken>
```

权限要求：

- 文档创建者可以查看。
- 已授权协作者也可以查看，便于前端展示参与人。

返回建议：

```ts
type DocumentCollaboratorVO = {
  id: number;
  documentId: number;
  userId: number;
  role: string;
  user: {
    id: number;
    username: string;
    account: string;
  };
  createdAt: string;
};
```

### 5.3 移除协作者

```http
DELETE /document/:docId/collaborators/:userId
Authorization: Bearer <accessToken>
```

权限要求：

- 只有文档创建者可以移除协作者。
- 不能通过这个接口删除 owner。

移除后的行为：

- 该用户后续不能再进入文档。
- 如果该用户已经在线，第一阶段可以等下次重连时失效。
- 更严格的方案是移除后通知协同房间踢出该用户连接。

### 5.4 修改协作者角色

第一阶段可以不做。后续需要 viewer/editor 切换时再加：

```http
PATCH /document/:docId/collaborators/:userId
Authorization: Bearer <accessToken>
Content-Type: application/json

{
  "role": "viewer"
}
```

## 6. 文档列表改造

当前 `/document/getList` 只返回自己创建的文档。共享功能上线后，建议改为返回两类文档：

- 我创建的文档。
- 分享给我的文档。

接口可以继续沿用：

```http
GET /document/getList
```

返回字段建议增加当前用户相对该文档的角色：

```ts
type DocumentListItem = {
  id: number;
  title: string;
  createdBy: number;
  createdAt: string;
  updatedAt: string;
  version: number;
  role: "owner" | "editor" | "viewer";
  creator: {
    id: number;
    username: string;
    account: string;
  };
};
```

查询逻辑：

```text
where:
  OR:
    createdBy = currentUserId
    collaborators.some.userId = currentUserId
```

## 7. 协同连接流程

共享权限上线后，`collab1` 和 `collab2` 的连接流程保持一致：

1. 前端携带 `docId` 和 `accessToken` 建立 WebSocket。
2. 服务端解析 token，拿到 `userId`。
3. 服务端查询文档。
4. 服务端调用统一权限校验。
5. 如果是 owner 或 editor，允许进入房间。
6. 服务端记录 `collaboration_sessions`。
7. 服务端加载或复用 Y.Doc 房间。
8. 开始 Yjs sync 和 awareness 同步。

拒绝场景：

| 场景 | 处理 |
| --- | --- |
| token 缺失或过期 | 关闭 WebSocket，reason `unauthorized` |
| 文档不存在 | 关闭 WebSocket，reason `document_not_found` |
| 用户不是 owner，也不是 collaborator | 关闭 WebSocket，reason `forbidden` |
| 用户是 viewer，但当前服务只支持编辑协同 | 关闭 WebSocket，reason `forbidden` 或进入只读模式 |

第一阶段建议只支持 owner/editor 进入协同，viewer 暂不开放 WebSocket 编辑。

## 8. 前端流程

### 8.1 创建者分享文档

1. 创建者打开文档设置或分享弹窗。
2. 通过账号、用户名或用户 ID 搜索目标用户。
3. 选择用户，调用添加协作者接口。
4. 添加成功后刷新协作者列表。
5. 被分享用户刷新文档列表后可以看到该文档。

### 8.2 被分享用户打开文档

1. 用户登录后调用 `/document/getList`。
2. 列表里展示自己创建的文档和分享给自己的文档。
3. 根据 `role` 展示权限标识。
4. 点击文档后，使用该文档 `id` 建立协同 WebSocket。
5. 服务端校验通过后进入协同房间。

### 8.3 移除协作者

1. 创建者在协作者列表里移除用户。
2. 前端调用删除协作者接口。
3. 成功后刷新协作者列表。
4. 被移除用户刷新列表后不再看到文档。
5. 被移除用户如果尝试重连 WebSocket，会被拒绝。

## 9. 与在线会话的关系

`document_collaborators` 和 `collaboration_sessions` 职责不同：

| 表 | 职责 |
| --- | --- |
| `document_collaborators` | 授权关系，表示谁有权访问文档 |
| `collaboration_sessions` | 在线状态，表示谁当前或最近进入过协同房间 |

不能用 `collaboration_sessions` 判断权限，因为用户断开连接后仍然应该保留访问权限；也不能用协作者表判断在线状态，因为有权限不代表在线。

## 10. 实现顺序建议

建议按下面顺序实现：

1. Prisma 增加 `DocumentCollaborator` 模型和迁移。
2. 增加协作者 DTO。
3. 在 `DocumentService` 增加添加、查询、删除协作者方法。
4. 在 `DocumentController` 增加协作者接口。
5. 改造 `YjsStorageService.validateDocumentAccess`，支持 owner 或 collaborator。
6. 改造 `/document/getList`，返回创建的和分享的文档。
7. 测试 owner、editor、未授权用户三种路径。
8. 前端接入分享弹窗、协作者列表和共享文档列表。

## 11. 后续增强

后续可以考虑：

- 增加 `viewer` 只读角色。
- 增加分享链接和邀请码。
- 增加组织/团队级共享。
- 移除协作者后主动踢出在线连接。
- 增加文档权限审计日志。
- 增加 owner 转让能力。
- 支持多个 owner 或 admin 角色。
